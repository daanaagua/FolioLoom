# FolioLoom Remotion 项目介绍视频设计

日期：2026-07-18

## 1. 目标

制作一支面向 B 站的横屏项目介绍视频，用较快节奏在 3–5 分钟内回答四个问题：

1. 为什么普通的 AI 分块翻译不足以处理长篇小说；
2. 为什么 AiNiee 等通用翻译项目没有覆盖本项目最关心的叙事连续性问题；
3. FolioLoom 用哪些通俗可理解的设计减少失忆、译名漂移和工程事故；
4. 观众如何在 GitHub 获取项目，并接入自己的模型 API 试用。

成片不把 FolioLoom 描述成能够弥补基础模型全部文学能力的万能工具，也不宣称最新版架构已经完成公开的全书质量基准。

## 2. 成片定位

- 发布平台：B 站；
- 画幅：16:9 横屏；
- 分辨率：1920 × 1080；
- 帧率：30 fps；
- 目标时长：约 4 分 20 秒，允许根据最终配音调整到 4 分 10 秒至 4 分 40 秒；
- 受众：小说读者、AI 翻译爱好者和开源项目开发者；
- 节奏：前半段用具体翻车案例建立问题，后半段才逐步展开工程设计；
- 配音：Fish Audio 的“曼波”声音模型；
- 叙述人称：第一人称“我”，不用“主播”自称。

## 3. 叙述身份与语气

视频明确说明：项目由用户持续提出问题、定义需求、判断译文并推动迭代，代码由 GPT 实现。用户不冒充代码作者，也不把自己的工作贬低成一次性生成。

建议使用以下表述：

> 我自己一行代码都没写。整个项目都是我把一次次翻译失败拆成问题，提出需求，再让 GPT 实现和反复测试出来的。

文案使用口语化短句，不朗读数据库表名、协议名、公式、哈希或内部类名。技术判断只在画面中保留少量可复查证据。

## 4. 叙事结构

最终时长由实际 WAV 决定，下列时间是剪辑目标而非硬编码帧数。

### 4.1 GitHub 冷开场（约 18 秒）

画面从 FolioLoom 的真实 GitHub 公开页开始。页面保持可辨识，标题、简介和 README 首屏依次进入焦点。

开场文案：

> 我原本只是想用 AI 翻几本没有中文版的长篇小说。结果很快发现：模型能翻好一句话，却不一定能翻好一整本书。

接着抛出问题：为什么为了翻一本小说，需要自己做一套翻译引擎。

### 4.2 长篇翻译怎样出错（约 40 秒）

连续展示四类问题：

1. 同一个名字在不同分块中出现多种译法；
2. 同一人物的别名、身份和称呼被误当成不同对象；
3. 单词字面翻对了，但没有恢复它在作品世界里的真实含义；
4. 场景、人物口吻和叙述语体在并行翻译后发生漂移。

落点文案：

> 单句能译，不等于整本书能译。长篇翻译真正难的，是模型翻到后面以后，还知不知道前面发生过什么。

### 4.3 与 AiNiee 的定位差异（约 20 秒）

比较只谈定位，不作笼统贬低：

> AiNiee 很适合通用文件、游戏文本和批量翻译。但我面对的是另一类问题：长篇小说里的叙事记忆、人物关系、译名漂移和并行任务之间的相互污染。它没有为这些问题提供完整答案，所以我只好自己继续研究。

断点恢复、多格式导入等通用能力不作为 FolioLoom 独有卖点。

### 4.4 五项核心设计（约 95 秒）

每个概念先展示原本如何损坏，再用一个简单动作解释 FolioLoom 的处理方式。

#### A. 原文不能偷偷少

原文导入后先按位置登记，每个文本块保留编号和内容指纹。翻译完成后逐块对账；少一块、重复一块或顺序错误都会被发现。

#### B. 翻到哪里，记忆开到哪里

系统不把全书背景一次性塞给模型。它只为当前段落取回真正相关、且在当前位置之前已经发生的事实，避免背景过多和后文信息提前泄露。

#### C. 统一的是人物，不是死词

人物名、别名和身份只有在证据足够时才合并；普通称呼则允许随语境自然变化。例如同一职业在叙述、自称和当面称呼中不必机械使用同一个中文词。

#### D. 可以一起干活，不能各自发明

一组并行任务开始前共享同一份译名和前情。返回顺序不会改变最终提交顺序；一个分块失败时不会污染相邻分块。

#### E. 哪里坏了，只修哪里

程序先检查漏段、原文残留、异常引号和已确认译名等可确定问题。发现错误时只抽出对应文本块返修，其余已通过内容保持不动。

### 4.5 实机流程（约 15 秒）

用真实命令和状态输出快速展示：

1. 导入一本 TXT、EPUB、DOCX 或 Markdown；
2. `doctor` 检查原文覆盖和分块；
3. 先运行一个窗口试译；
4. 确认后继续全书；
5. `audit` 审计并导出 TXT、双语 TXT 和报告。

命令只展示关键行，不让观众阅读长串参数。

### 4.6 皮亚顿案例与翻译成果（约 40 秒）

这一段不假设观众读过《新日之书》，也不复述整段原文。

配音文案：

> 小说里，主角遇到了一个双头人。能正常说话的那颗头自称提丰。为了给自己续命，他把自己的头移植到了奴隶皮亚顿身上。本来等神经接管完毕，皮亚顿原来的头就会被切掉；但手术没能完成，皮亚顿仍然活着，也还控制着这具身体的心跳，只是几乎说不出话。
>
> 所以这个双头人并不是一个长了两颗头的怪物，而是两个意识被困在了同一具身体里。后来，皮亚顿悄悄动嘴提醒主角。主角没有攻击看起来更强势的提丰，反而打向皮亚顿；皮亚顿一死，心脏停止，提丰也跟着死了。
>
> 我希望翻译系统记住的，不只是“Piaton 应该音译成皮亚顿”，而是这个人到底是谁，以及前后的因果为什么能够成立。

画面只使用原文短句、中文解释、高亮和证据线，不绘制提丰身体或人物 SVG。三个关键事实依次汇聚：

1. 提丰被移植到皮亚顿身上；
2. 皮亚顿仍保有头颅和心跳控制；
3. 主角攻击皮亚顿后，两人随同一具身体死亡。

片中可以短暂展示真实工程结果：同一局部目标的冷启动从约 3 小时 25 分缩短到 4 分 24 秒、5/5 文本块落盘、最终校验失败为 0。字幕必须注明这是同一段局部试译，不外推为全书速度承诺。

盲评结果以一句话诚实交代：同一 Flash 模型的五段对照中新内核两胜、一负、一平、一项都不理想。结论是架构能减少失忆、漂移和工程事故，但不能把小模型直接变成文学大师。

### 4.7 路线图与邀请（约 25 秒）

画面回到 GitHub README，滚动至当前限制、快速开始和未来方向。

结尾文案：

> FolioLoom 现在已经公开在 GitHub。想体验的朋友，可以接入自己的模型 API，拿一小段有权处理的文本先试试看。后面我还准备给它补上 GUI、更多 API 接口，以及 Galgame、MTool 和其他文本格式的支持。

## 5. 视觉系统

### 5.1 GitHub 是主舞台

真实 GitHub 公开页的高清长图承担开场、章节间返回和结尾。README 通过遮罩内的纵向位移模拟真实滚动。镜头需要解释一个概念时，先推进并高亮对应 README 文句，再进入独立概念画面；讲解完成后，元素收回并返回同一页面位置。

正式渲染不访问网络。GitHub 页面只在素材准备阶段捕获一次。

### 5.2 动效语言

- 动画使用克制的推进、焦点变化、文字汇聚、段落展开和局部抽离；
- 单个概念画面原则上不超过 18 秒；
- 每 25–35 秒回到一次 GitHub 主舞台；
- 不使用弹跳卡片、夸张霓虹、人物简笔画或粗糙 SVG；
- 皮亚顿案例以短句和证据关系表达，不画双头人物；
- 技术参数退居背景，字幕只保留观众能立即理解的结论。

### 5.3 排版与色彩

- GitHub 主舞台沿用真实页面的深色界面；
- 解释性书页使用偏暖纸张色和宋体/衬线体；
- 工程证据使用等宽字体；
- 主强调色采用 GitHub 蓝，错误使用克制的珊瑚红，通过使用绿色；
- 字幕保持高对比度并落在 16:9 安全区内。

## 6. 配音与字幕

使用用户指定的 Fish Audio 曼波生成器：

`https://fish.audio/zh-CN/m/0f08cacd3e354471a4b94dd00b4cc4a3/`

流程如下：

1. 先锁定完整文案；
2. 按场景拆成短音频，每段保留自然语气和停顿；
3. 在 Fish Audio 手动生成并下载 WAV；
4. 文件按 `01-opening.wav`、`02-problems.wav` 等稳定名称保存；
5. Remotion 读取真实音频时长决定场景长度；
6. 字幕按短语而非逐字显示，同时导出独立 SRT。

V1 不自动调用 Fish Audio API，不在仓库中保存账号、Cookie、Token 或声音文件。声音模型的使用权限和最终视频的发布条件由用户在生成时自行确认。

## 7. 工程组织

### 7.1 仓库内源码

在 FolioLoom 仓库增加 `video/`：

```text
video/
  package.json
  src/
    Root.tsx
    FolioLoomIntro.tsx
    script.ts
    theme.ts
    components/
    scenes/
  scripts/
    capture-github.ts
    prepare-assets.ts
    preflight.ts
  config/
    project.local.json.example
  public/
    generated/          # Git 忽略
  out/                  # Git 忽略
```

仓库只保存可复用的 Remotion 源码、公开文案和空白配置示例。

### 7.2 仓库外素材

默认本机素材根目录可设为：

`D:\llm\qikan4\folioloom-video-assets`

其中保存：

```text
github/github-readme.png
voice/*.wav
excerpts/*.txt
```

实际路径写入被 Git 忽略的 `video/config/project.local.json`。小说原文、译文节选、曼波语音和最终 MP4 不进入公开仓库。

### 7.3 场景组件

最少包含以下可独立预览的场景：

- `GithubStage`：真实 GitHub 长图、滚动和焦点推进；
- `ProblemMontage`：四类长篇翻译问题；
- `AinieePositioning`：定位差异；
- `LosslessSourceScene`：原文登记与缺块；
- `NarrativeMemoryScene`：按位置开放记忆；
- `EntityContextScene`：人物统一与语境变形；
- `ParallelWaveScene`：共享前情的并行任务；
- `LocalRepairScene`：确定性检查和局部返修；
- `WorkflowScene`：命令行实机流程；
- `PiatonCaseScene`：皮亚顿证据汇聚；
- `RoadmapScene`：GUI、API 和格式扩展。

## 8. 数据流

1. `capture-github.ts` 在人工需要更新页面时捕获一次真实 GitHub 长图；
2. 用户在 Fish Audio 手动生成各场景 WAV；
3. 外部素材和路径写入本地配置；
4. `prepare-assets.ts` 校验文件类型、大小和存在性，将需要渲染的素材复制到 `video/public/generated/`；
5. `script.ts` 提供逐场文案、字幕短语、README 滚动目标和场景顺序；
6. 组合根据 WAV 时长与场景间隙计算总帧数；
7. Remotion 输出低清草稿、1080p 正片和 SRT；
8. 输出留在本机 `video/out/`，除非用户另行决定发布。

## 9. 错误处理

预检遇到以下任一情况必须失败并停止渲染：

- 本地配置缺失或引用不存在的文件；
- WAV 无法读取、时长为零或场景缺少对应音频；
- GitHub 长图尺寸不足或比例不符合滚动要求；
- 字幕为空、结束时间超过场景或超出安全区；
- 素材缓存或配置中出现 API Key、Cookie、Token 或不应公开的本机绝对路径；
- 成片总时长超出 3–5 分钟目标；
- 关键场景没有对应的文案或镜头定义。

渲染阶段不得静默联网下载缺失素材，也不得用占位音频冒充完成。

## 10. 验证与验收

### 10.1 自动检查

- TypeScript 类型检查；
- 场景表中 ID 唯一、顺序连续；
- 音频与场景一一对应；
- 根据音频计算的帧数和 SRT 终点一致；
- 所有字幕处于安全区并满足最大行数；
- 外部素材目录、缓存目录和输出目录均被 Git 忽略；
- 对源码、配置和生成清单进行密钥模式扫描；
- 关键帧渲染可以在无网络环境完成。

### 10.2 视觉验收

1. 为每个场景渲染开头、中段和结尾关键帧；
2. 检查 GitHub 页面文字是否可辨识、镜头是否错误裁切；
3. 检查概念动画是否比静态卡片更自然；
4. 检查皮亚顿段没有人物 SVG，未读原著的观众也能理解；
5. 先渲染 480p 草稿确认节奏、停顿和字幕；
6. 再渲染 1080p 正片，核对音画总时长、SRT 终点和结尾静帧。

### 10.3 内容验收

- 不把 AiNiee 描述成劣质项目，只说明适用问题不同；
- 不把断点恢复和格式导入冒充独有设计；
- 不声称最新版 FolioLoom 已完成全书质量基准；
- 局部速度数据保留范围说明；
- 盲评结果不隐瞒负面或平局；
- 用户的角色表述为提出问题、设计需求和推动测试，代码由 GPT 实现；
- 结尾明确要求观众使用自己的模型 API，并只处理有权使用的文本。

## 11. 非目标

第一版不包含：

- 自动调用 Fish Audio API；
- 逐字卡拉 OK 字幕；
- 复杂人物插画、3D 模型或角色 SVG；
- 视频内 GUI 原型演示；
- 自动发布 B 站；
- 背景音乐授权与混音；
- 通过视频承诺某一模型的固定翻译质量或费用。

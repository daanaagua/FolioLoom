日期：2026-07-17  
结论：`promote`——合并为实验性 V5 sidecar，继续承担局部试译与架构验证；暂不替换 V4 全书生产流程。

## 4. Agent 实际做了什么

Question Scout 提交了一个高影响问题：数据库中两个都映射为 `Piaton` 的 concept ID 是否指同一实体。Evidence Search 只调用了 subject/term lookup 与 mentions 搜索；Evidence Finalizer 用 evidence ID 提交结论，判断二者都是皮亚顿这一实体的不同记录。该结论置信度为 1，进入 translator-global 通道；没有 unresolved 问题。

全局词汇表没有锁定 `Conciliator`。并行翻译前，Lexical Anchorer 在固定脚本给出的两项跨岛重复候选中，将：

- `Conciliator` 判为 `stable`，绑定“调和者”，置信度 0.95；
- `Talisman-bearer` 判为 `contextual`，不建立强制表面译名。

最终两个 `Conciliator` 出现位置都译为“调和者”。这说明锚点不只是提示：Kernel 会逐 block 校验 stable 目标，偏离即进入局部修复。

Agent 没有扫描 0..218 前缀、没有读取叙事快照、没有 shell/read/edit/任意 SQL 权限，也没有把低置信研究判断直接塞给翻译模型。

## 5. 质量审计

最终中文 TXT：

- 5 块均落盘，共 148 个非空段落；
- 没有相邻完全重复段落；
- 没有普通英文残留，拉丁字母只剩章节号 `XXIV/XXV/XXVI`；
- 没有 ASCII 双引号、直角引号或异常引号字形；
- 中文双引号为 113 个开、112 个闭；多出的一个开引号对应原文跨段连续讲话的边界，不是凭空丢失闭引号；
- `Typhon/Piaton/Severian/Claw` 分别稳定为“提丰/皮亚顿/塞万里安/利爪”；
- `Conciliator` 的两次出现都遵守运行时锚点“调和者”。

真实试跑先后暴露并修复了：V4 块边界的重复段落、普通英文漏译、引号字形漂移、修复补丁误删正常 block、研究阶段耗尽提交预算、低置信解释进入翻译上下文、并行 island 的术语漂移，以及修复补丁引入新错误后不再复检等问题。每项都已转成确定性约束或有硬预算的阶段协议，而非针对某个具体译词做替换。

本次人工抽查认为译文已达到可直接阅读的试译稿水平，但尚未完成与 V4、旧 DOCX 或 Pro 模型的正式盲评，因此不能据此宣称文学质量全面优于既有方案。

## 6. 架构判断

本次结果支持以下判断：

1. Pi 适合承担问题登记、有界检索、证据终结、跨岛词汇锚定和局部修复；Kernel 必须掌握预算、可见性、提交、校验和重试。
2. “把所有背景塞进翻译提示”不是必要条件。目标原文、稳定术语、高置信事实和按需工具足以完成本段。
3. Agent 的自由循环必须按子阶段切预算。研究采用 Scout（最多 3 turn）→ Search（2 turn/6 工具）→ Finalizer（2 turn/独占提交工具），避免检索耗尽提交预算。
4. 并行岛之间必须先建立共享锚点，并把 stable 锚点升级为校验约束；单纯提示无法阻止模型漂移。
5. 修复必须是按 block ID 合并的最小补丁，并在全局三轮上限内对新失败继续复检。

## 7. 推进决定与下一步

决定为 `promote`：将 V5 sidecar 合并到 `main`，保留为实验入口。它已经证明局部冷启动可以在严格边界内自动跑完，并比 V4 cold/warm 都快。

下一轮最小工作不是继续扩大 Agent 自由度，而是：

1. 把本次输出接入现有盲评页面，与 V4 旧译和 DeepSeek Pro 同段对比；
2. 在 3—5 个不同题材、不同位置的局部窗口重复测试候选词分类与引号校验；
3. 盲评通过后，再设计 V5 provisional snapshot 向正式 SQLite 工作库的事务提交；
4. 全书模式另行测量缓存、批次调度和跨窗口锚点持久化，不直接把本次局部比例外推到整书。
